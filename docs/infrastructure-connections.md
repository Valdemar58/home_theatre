# Локальные подключения

Единственный рабочий файл: `~/.config/home_theater/infrastructure.json`.
На Windows `~` — пользовательская папка, например
`C:/Users/USER/.config/home_theater/infrastructure.json`; на Linux — `/home/USER`.
Файл находится вне репозитория и временных worktree, поэтому не попадает в Git
и не исчезнет при смене ветки или удалении worktree. Публичный шаблон —
`docs/examples/infrastructure.example.json`. При переходе на другой компьютер
перенесите рабочий файл отдельно; пути к ключам/kubeconfig при необходимости поправьте.

Это единый перечень подключений для работы над инфраструктурой. Он не является
настройкой приложения и пока не загружается установщиком автоматически.
Заполнение файла не запускает подключение или развёртывание. `enabled: false`
означает, что запись — заготовка; перед работой явно включите нужную запись.

## Первый VPS

В `servers.production` заполните `ssh.host`, `ssh.user` и при необходимости
`ssh.port`, затем поставьте `enabled: true`. Ubuntu 24.04 остаётся целевой ОС R3.
Если вход пока по паролю, оставьте `authentication: "password-interactive"`:
пароль вводится интерактивно, его не нужно сохранять здесь или отправлять в чат.

Для ключа укажите `authentication: "agent-or-key"` и абсолютный `identityFile`
(например `C:/Users/USER/.ssh/id_ed25519` или `/home/USER/.ssh/id_ed25519`).
Если ключ уже загружен в SSH-agent, путь можно оставить пустым.
Альтернатива — `configHost`: существующий Host из `~/.ssh/config`; тогда параметры
этого профиля имеют приоритет, а `host/user/port` в JSON не дублируют его.
Проверка ключа хоста остаётся штатной SSH; неизвестный/изменившийся ключ не
принимается автоматически. Имена, порты и роли — данные, не shell-команды.

## Роли и несколько серверов

Один сервер может иметь несколько `roles` и несколько `services`. Например,
приложение и Unleash могут жить на первом VPS; наблюдаемость — на другом.
Чтобы вынести Unleash, создайте новую запись сервера с ролью `feature_flags` и
перенесите к ней описание `services.unleash`. Названия записей произвольные:
можно добавить `development`, `backup` и другие. Неиспользуемые примеры можно
удалить или оставить выключенными. Пустой URL означает «ещё не настроен».

`services` хранит адреса и рабочие каталоги, но не создаёт сервисы и не выбирает
за вас стек наблюдаемости. Выбор состава и установка будут отдельной работой.

## Kubernetes

SSH к отдельным узлам описывается в `servers`; управление кластером через API —
в `clusters`. Укажите абсолютный `kubeconfigFile`, точный `context` и namespace.
Не полагайтесь на текущий глобальный context kubectl. В kubeconfig остаются
сертификаты/токены; их содержимое сюда не копируется. Кластер можно описать,
даже если SSH к его узлам недоступен. Kubernetes не входит в обязательную 1.0.

Не копируйте заполненный файл в отслеживаемые каталоги репозитория. Каталог
`.local/` дополнительно исключён из Git для локальных материалов; вторую рабочую
копию конфигурации там создавать не нужно. Хранение вне Git не шифрует файл:
не сохраняйте в нём пароли, приватные ключи или API-токены.
