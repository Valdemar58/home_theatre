# R6 — сквозная приёмка 1.0

Проверяется пригодность сервера и Windows desktop к личному использованию.
Arch остаётся preview. Зелёные unit-тесты и локальная комната не заменяют
проверку двух реальных сетей; исключения принимает владелец по конкретным пунктам.

## R6.0 · подключение через VPN, #99

Владелец подтвердил: при включённом VPN сайты в браузере открываются.
Проверка выявила рабочий HTTP/SOCKS-прокси и переменное время холодного TLS:
туннель открывался за миллисекунды, ожидание первого TLS-ответа было существенно
дольше; сертификат после получения проверялся быстро и без ошибок.
Свежий Chrome также открывал endpoint около 12 секунд. Поэтому прежний предел
15 секунд мог преждевременно блокировать desktop; это не доказательство
неработоспособности VPN или несовместимости протокола.

В rc.18:
- handshake, native API, аккаунт и web используют соответствующую сессию профиля;
- первоначальное подключение ограничено общим бюджетом 45 секунд;
- только анонимный read-only handshake может повториться один раз после
  транспортного обрыва, в том же бюджете и по тому же маршруту;
- вход, команды, отрицательные ответы и несовместимый manifest не повторяются;
- UI различает соединение через прокси, проверку контракта и транспортную ошибку;
- прямого fallback, зашитого IP и изменений Windows/VPN нет; TLS проверяется.

Локальные доказательства: 65 desktop-тестов; настоящий Electron с медленным
контролируемым прокси, cookie-free handshake и общей сессией web/native;
три свежих профиля открыли prod через включённый системный прокси примерно за
3 секунды. На 360/1140 px проверены соединение, повтор, проверка контракта и
ошибка. Исходные JSON/скриншоты — `.local/r6-proxy/`, не включают реальные пароли.
PR #100 объединён, кандидат rc.18 опубликован; Windows/Linux CI и проверка
анонимных update feeds прошли. #99 оставлена «На проверке»: приёмка владельцем
ещё не получена.

### Исходный прогон 2026-11-21

Отдельный Compose `home-theater-r6-e2e`, порт 5094, собственные PostgreSQL и
тома; серверный image digest `ce7efa47…` совпадает с R5.4 prod. Персональные
prod/dev БД и профиль установленного desktop не изменялись. Два созданных
тестовых аккаунта прошли выдачу доступа по приглашению, дружбу и вступление
в комнату. Desktop прошёл мастер первого запуска, синхронизацию и привязку;
повторная привязка вернула тот же ID, `alreadyLinked=true`.

Поиск проверен на контролируемом индексере, загрузка — настоящим BitTorrent
с localhost-пира, подготовка — настоящим FFmpeg. Для torrent и magnet выбраны
серии 1 и 3 из трёх, по 30 858 537 байт; серия 2 отсутствует в библиотеке.
Частичный прогресс подтверждён также в DOM, а не только в API: общий 18/100
(скачано 22%), серия 1 — 35/100 (скачано 44%). Это **не** проверка доступности
внешних трекеров или реальных релизов; она остаётся в #39.

Серверная ретрансляция на стенде явно отключена. Одиночный и совместный
просмотр в Chrome воспроизводили видео через RTCDataChannel с ненулевыми
`bytesReceived`; зрителю desktop не устанавливался. В двух локальных
браузерах разница позиций около 0,5 с, общая пауза и ручной переход 1 → 3
подтверждены. Это не заменяет WAN, мобильный браузер, автопереход или смену хоста.

Найдены: #101 (вход ведёт в календарь), #102 (неявно включённый relay и его
диагностика), #103 (Windows EPERM при сохранении библиотеки). Для #103 добавлены
ограниченные повторы атомарной замены без удаления последнего корректного
файла и восстановление импорта; повторный полный magnet-прогон прошёл.
71 desktop-тест прошёл, включая временную/постоянную ошибку записи и повтор
импорта без дубликатов. Само успешное повторение не доказывает конкретную
причину Windows-блокировки файла.

Исправление #103 объединено PR #104 (`b2c415bf…`), CI Windows/Linux прошёл.
В опубликованный rc.18 оно не входит; установленное приложение не обновлялось.

Локальные артефакты: `.local/r6-e2e/screenshots/01…33`, `screenshots.html`, `download-proof.json`,
`magnet-regression-proof.json`, `visible-progress.json`, `playback-proof.json`,
`joint-proof.json`, `manual-transition-proof.json`. Каталог также содержит
секреты **тестового** стенда: публиковать его целиком нельзя. Для передачи
владельцу используются только скриншоты и очищенные сводки.

## R6.2 · восстановление и синхронизация, #24

Авто/ручные переключения серий, переходы тайтлов, перерывы, автовоспроизведение;
потеря хоста с буфером, одинаковая версия запасного файла, удержание и пропуск
отставшего; возврат зрителя, потеря сервера и восстановление истории/прогресса.
Автоматические проверки — отдельно от фактического прогона браузеров.

В двух реальных локальных Chrome-контекстах на том же изолированном сервере
проверен план A:[1,3] → перерыв 1 минута → C:[1]. Конец серии получен от video
после синхронной перемотки к 55-й секунде 60-секундного ролика: общий отсчёт,
автопереход к серии 3 без повторной готовности, общий перерыв, выключение
автовоспроизведения до конца отсчёта, ожидание организатора после нуля,
включение и автозапуск C:1, завершение со статусом `done`. Эти перемотки
не использовались как доказательство зачёта 80%.

Отдельный сеанс A:1 воспроизведён непрерывно с нуля до конца. Серия появилась
в личных историях обоих аккаунтов и результате встречи. Через API отдельно
проверены preview исправления завершённой встречи, запрет исправления зрителю,
журнал организатора, отмена участником отметки за него, сохранение группового
результата после личной отмены и отклонение устаревшей revision (409).
UI редактора исправлений этим API-прогоном не проверен.

Доказательства: `planned-proof.json`, `coverage-proof.json`, `history-proof.json`;
скриншоты 28–33.

### Обрыв хоста · 2026-11-21

Два полных Electron-приложения с разными изолированными профилями и разными
ID устройств, отдельные физические копии синтетических исходных/подготовленных
файлов. Оба устройства привязаны обычным мастером; подготовленный MP4 имеет
одинаковые SHA-256 и размер. Зрители — два отдельных аккаунта в Chrome;
HTTP relay на стенде выключен. Это две нативные программы на одном Windows ПК,
а не два физических компьютера в независимых сетях.

| Сценарий | Фактический результат |
| --- | --- |
| Аварийное завершение основного Electron | При запасе 10,56 / 14,13 с оба клиента автоматически перешли на второй Electron. Переключение и контрольное чтение заняли 7,47 с. Паузы/waiting/смены URL после обрыва не было; разница позиций 0,39 с. |
| Источник новой передачи | У обоих lease устройство стало запасным, generation=2. Новое RTC-соединение установлено; через него выполнено контрольное чтение 1 МиБ. Серверный relay выключен. |
| Уведомление | Зафиксированы «Связь с хостом потеряна · ищем доступную копию» и «Хост заменён · продолжаем с того же места». |
| Нет разрешённой резервной копии | После исчерпания буфера общая пауза примерно на 20,4 с. До возвращения доступной копии самопроизвольного продолжения нет. Разрешение запасного хоста возвращено; оба продолжили без кнопки play, разница 0,29 с. |
| Один зритель не может восстановить канал | Только его сигнализация заблокирована и RTC закрыт; координация комнаты остаётся доступной. Буфер исчерпан, общая пауза. Организатор нажал в UI «Продолжить без ожидающих»: остальные продолжают, повторного hold в проверенном интервале нет. |
| Возвращение исключённого зрителя | После снятия сетевой блокировки восстановление и догон общей позиции автоматические, без «Продолжить всем»/reload; разница 0,039 с. |

Отдельно 35 серверных тестов прошли на Node с `node:sqlite`: другой encode,
отсутствующее разрешение, устаревший heartbeat, ответы старого поколения,
отзыв доступа, отсутствие автоматического возврата на прежний хост, барьер
и отсутствие автоматического исключения по таймеру. Эти отрицательные случаи

Артефакты: `failover-proof.json`, `exhaustion-proof.json`, `late-viewer-proof.json`,
`recovery-server-tests.log`; скриншоты 34–47 в `.local/r6-e2e/`.

## R6.3 · разные сети, #25

Хост Windows и зритель в другой реальной сети. Прямой WebRTC, рабочие условия
NAT/firewall, понятная диагностика неуспеха. TURN в 1.0 не обещан. Нужна помощь
владельца/друга. Владелец подтвердил второе устройство через мобильный интернет;
проверка ещё не выполнялась.

Read-only проверка VPS показала: image R5.4 `ce7efa47…`, healthy,
автосмена включена, `DESKTOP_STUN_URLS` не задан, HTTP relay включён по умолчанию.
Настройки не изменялись. Поэтому успешный запуск через мобильную сеть сам по
себе ещё не докажет прямую передачу: нужно смотреть фактический маршрут.
Подготовка и критерии проверки: [инструкция R6.3](release-1.0-r6-mobile-check.md).

После этого владелец разрешил окно до 10 минут. На том же образе применены
`DESKTOP_STUN_URLS=stun:stun.cloudflare.com:3478` и `DESKTOP_RELAY_ENABLED=0`.
Штатная резервная копия проверена; fingerprint данных аккаунтов, истории и
привязок совпал, образ/installation.json не менялись. После обслуживания
HTTPS/health/handshake успешны; свежий desktop открыл prod login через
системный HTTP proxy за 3,8 с. Проверен приём srflx-кандидата с текущего ПК
примерно за 0,75 с (отдельные интерфейсы не отвечают/медленнее).

Первая процедура защитно вернула прежнюю конфигурацию: проверка handshake
была ошибочно выполнена во время обслуживания и получила штатный 503.
После исправления порядка проверки повтор завершился в согласованном окне.
Артефакты — `production-network-update-final.log`, `production-network-result.json`,
`production-desktop-proof.json`, `stun-probe-proof.json`. Сетевой видеопрогон
с мобильным устройством остаётся за владельцем; успешный HTTPS его не заменяет.

## R6.4 · закрытие проблем, #26

### Блокер основного поиска, #112

Реальный desktop rc.20 показал «Поиск раздач не подключён» на prod:
в установке отсутствовал модуль search. Предыдущие локальные проверки
не подтверждали готовность продакшена; выдавать инструкцию WAN-прогона
до проверки этой цепочки было преждевременно.

После явного разрешения владельца на VPS установлен только Prowlarr
с публичными Nyaa.si и RuTor. Приватные индексаторы и их авторизация
из dev не переносились. Подключение выполнено с проверенным pre-update
бэкапом; образ приложения, аккаунты, история и привязки сохранены.
STUN сохранён, HTTP relay выключен; видео загружается на desktop.

Обнаружен отдельный дефект фильтра: RuTor относит аниме к Other (8000),
а приложение запрашивало только TV/Anime. На том же индексаторе точное
русское название «О моём перерождении в слизь» даёт 35 результатов
с учётом 8000 и ноль без него. PR #113 добавляет эту категорию только
для определения rutor, обновляет ключ кэша схемы индексаторов и проверяет
частичный/полный отказ. Обязательный PR CI и сборка кандидата прошли.
После отдельного разрешения владельца приложение VPS обновлено до
`94b82f8` / digest `851ffd1d…` с проверенным бэкапом и сохранением данных.
В реальном desktop подтверждена выдача RuTor по исходному русскому названию,
в том числе S01 (2018) с русскими дорожками. Новая версия desktop не нужна.

В установленном пользовательском desktop через Nyaa найдена реальная
magnet-раздача S01, получены метаданные и выбран только S01E01 (694 371 752
байта). Загрузка на домашний ПК и автоматическая подготовка завершены:
MP4 940 182 450 байт, длительность 1423,098 с. Воспроизведение в установленном
desktop реально продвинулось с 2,16 до 18,36 с, затем поставлено на паузу;
плашка «С хоста напрямую». Копия разрешена комнате «123» (группа 1),
в её панели хост онлайн и серия 1 подготовлена. WAN-прогон с телефоном
остаётся непроверенным, это не приёмка R6.3.

В существующем активном просмотре группы 1 через UI выбран источник
`valde · DESKTOP-M0M6ER5` вместо серверной библиотеки. Плеер комнаты
показал «С хоста напрямую», общая позиция около нуля, состояние — пауза.
Новый просмотр/приглашение не создавались. Для первого телефонного теста
достаточно войти другим участником в эту группу и присоединиться к просмотру.

Наблюдавшиеся временная ошибка handshake и устаревшие 41% подготовки
совпали с обслуживанием; после повторной проверки соединение восстановилось,
готовый файл распознан. Принудительная остановка FFmpeg не потребовалась.
Отдельная проблема выбора файлов многосезонной раздачи записана в #114.

#43, #44, #46, #76, #101–#103, #106 и новые найденные регрессии; проверка выбранных интеграций
#39. Название/единая конфигурация/иконка #48–#50 согласуются до финальной упаковки.
Ни один непроверенный компонент не считается исправным по наличию контейнера.
Приёмка R6 предшествует финальным пакетам и публикации R7.
