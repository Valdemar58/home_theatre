# Установка серверного кандидата

R3 проверяет установку на отдельном VPS. Это не стабильный выпуск 1.0 и не перенос
рабочих данных: текущая установка продолжает работать. Поддерживается Ubuntu
Server 24.04 LTS x86_64. На сервере не скачиваются и не раздаются серии.

## Установка

Пакет `server-candidate` собирается явным запуском GitHub Actions **Server candidate**
из `main`, после обязательного CI. Он содержит SHA исходников, digest образа GHCR,
установщик и контрольную сумму. VPS получает готовый образ; Node и компилятор ему
не нужны. По умолчанию устанавливаются приложение и PostgreSQL.

Скачать оба файла из одного запуска Actions, загрузить на VPS и выполнить:

```sh
sha256sum --check server-candidate.tar.gz.sha256
tar -xzf server-candidate.tar.gz
sudo bash scripts/install.sh --origin https://test.example.org
sudo /opt/home_theater/home-theater doctor
```

Перед публичной установкой A/AAAA домена должны указывать на VPS; нужны входящие
80/TCP и 443/TCP. Caddy получает сертификат автоматически. Неиспользуемую AAAA
запись следует удалить. Установщик не меняет SSH, firewall, чужие контейнеры и
системный DNS. Порты PostgreSQL, приложения и модулей не публикуются в интернет.

Без домена сначала использовать `--origin http://127.0.0.1:5056` и SSH-туннель
`ssh -L 5057:127.0.0.1:5056 <ssh-profile>`. Открывать `http://127.0.0.1:5057`.
Для ссылки настройки в таком туннеле заменить **только origin** на локальный адрес
туннеля; фрагмент токена не менять и не публиковать. HTTP по внешнему IP запрещён.

После настройки DNS явно переключить эту же установку на HTTPS, сохранив данные:
`sudo /opt/home_theater/home-theater origin https://test.example.org`.

При необходимости Docker устанавливается из официального APT-репозитория.
Существующий Docker сохраняется, проверяется наличие Compose v2. Пользователь не
добавляется автоматически в группу docker. Для установки нужны sudo и минимум
4 GiB свободного места; LLM-модели требуют дополнительного пространства.

## Владелец и восстановление

```sh
sudo /opt/home_theater/home-theater owner-link
sudo /opt/home_theater/home-theater reset-password --user-id 1
```

Первая команда применима только к пустой установке без владельца. Одноразовая
ссылка действует один час, показывается только по явной команде и не попадает в
логи установщика. Нет пароля по умолчанию и автоматического одобрения регистраций.
Существующий admin и его история остаются в прежней системе до отдельного переноса.

## Дополнительные компоненты

```sh
sudo bash scripts/install.sh --origin https://test.example.org --modules search
sudo /opt/home_theater/home-theater module search on
sudo /opt/home_theater/home-theater module search off
sudo /opt/home_theater/home-theater module llm on
```

`search` устанавливает Prowlarr и автоматически подхватывает его API-ключ. Индексаторы
настраиваются отдельно в его панели через SSH-туннель на 9696. Без индексаторов
поиск пуст; установка контейнера не означает готовность источников. Скачивание
выполняет desktop. `llm` устанавливает Ollama без моделей; модель загружается отдельно
после оценки ресурсов. HTTPS включается при установке с HTTPS origin.

Отключение не удаляет данные компонентов. Отсутствие поиска не мешает аккаунтам,
планированию и импорту torrent/magnet; отсутствие LLM не удаляет сохранённые знания
и метаданные API. Админская диагностика возможностей и полный аудит деградации
относятся к R3.2. Внешние интеграции можно настраивать в приватном `application.env`;
управляемые URL Prowlarr/Ollama обслуживает установщик.

## Состояние установки

`/opt/home_theater/installation.json` хранит origin, модули и зафиксированные digest.
`server.env` и `application.env` содержат секреты, доступны root. Не копировать их в
Issues, логи CI или Git. Повторный запуск установщика сохраняет секреты, БД, данные,
конкретные образы и состав модулей; изменение образа/домена не выполняется молча.
Использовать `module` для явного изменения состава. Именованные тома Compose
отделены от других установок; запрещено применять `down -v` к рабочим данным.

## Резервное копирование

```sh
sudo /opt/home_theater/home-theater backup
sudo /opt/home_theater/home-theater verify-backup /opt/home_theater/backups/backup-....tar.gz
sudo /opt/home_theater/home-theater restore /opt/home_theater/backups/backup-....tar.gz
```

Архив содержит PostgreSQL, секреты, конфигурацию, пользовательские файлы и настройки
Prowlarr. Серии, Ollama-модели и восстанавливаемые кэши изображений/страниц исключены.
Файл доступен только root; checksum каждого файла проверяется до завершения копии.
Архив содержит секреты: передавать и хранить его с теми же ограничениями, что и доступ
к серверу. Локальная копия не защищает от потери VPS; её можно забрать по SSH.

Для согласованного снимка приложение и пишущий конфигурацию Prowlarr ненадолго
останавливаются и затем запускаются в прежнем составе. При активных комнатах команда
отказывается делать это без окна обслуживания. Автоматического ежедневного прерывания
просмотра нет.

Восстановление требует того же digest приложения. Сначала архив проверяется и
разворачивается в новую БД; прежняя БД не перезаписывается. Перед переключением
создаётся копия текущего состояния. Сохраняются origin, порты, проект и пароль
PostgreSQL целевой установки; пользовательские сессии и привязки восстанавливаются
вместе с исходным SESSION_SECRET. Старые файловые каталоги остаются с суффиксом
`before-restore`, пока владелец явно их не удалит. При ошибке запуска возвращается
предыдущее состояние. Не выполнять восстановление на работающем просмотре.

Опциональное ежедневное расписание установлено, но выключено на новой установке:

```sh
sudo /opt/home_theater/home-theater daily-backup on
sudo /opt/home_theater/home-theater daily-backup off
```

Хранятся 7 ежедневных копий и последняя предобновительная. Ручные и предвосстановительные
копии автоматически не удаляются. Расписание использует время ОС и не прерывает
активные комнаты: при их наличии копия не создаётся, причина видна в systemd journal.
Повторная установка расписания сохраняет выбранное владельцем состояние.

## Плановое обновление R3.4

Команды доступны в кандидате с maintenance protocol 1. Скачать и сверить checksum
нового пакета, распаковать его в отдельный каталог. Указать `deploy/server` этого
пакета и время с явным часовым поясом:

```sh
sudo /opt/home_theater/home-theater schedule-update \
  --bundle /root/new-candidate/deploy/server \
  --at '2026-12-01T20:00:00+01:00' --window-minutes 10
sudo /opt/home_theater/home-theater cancel-update
```

Дата приведена как пример: выбрать фактическое будущее окно. Образ скачивается
заранее; если загрузка не завершилась до назначенного времени, план не создаётся.
Расписание хранится systemd, поэтому закрытие SSH не отменяет обновление. До начала
окна его можно отменить командой выше. Одновременно разрешён один план на установку.

За 15 минут появляется предупреждение с отсчётом; за 5 минут меняется его текст.
Уведомление доступно и в полноэкранном контейнере плеера. В начале окна блокируются
новые операции, сохраняется общая позиция комнат, отключаются автопереходы и
останавливается локальное воспроизведение. Существующие плееры имеют 10 секунд
для финального отчёта позиции; затем обновлятор ждёт завершения серверных задач.
Независимые загрузки desktop продолжаются; новые команды с сервера временно
недоступны. Если безопасная остановка или бэкап не уложились в окно, применение
кандидата отменяется. Начатое применение/откат доводится до результата, даже если
окно истекло: прерывать миграцию по таймеру небезопасно.

После проверенного предобновительного бэкапа применяются образ и файлы установщика,
выполняются штатные миграции приложения и readiness. При отказе возвращаются прежние
файлы, образ и данные из копии через новую БД; исходная БД сохраняется. При отказе
автоматического восстановления обслуживание остаётся включённым для ручного разбора.
После успешного обновления или восстановления просмотр остаётся на паузе: пользователь
обновляет страницу и продолжает с сохранённого места, бесшовность не обещается.

Старые первоначальные кандидаты без `/api/maintenance` таким обновлятором не
обновляются: для первого перехода требуется отдельное согласованное окно и
контролируемое первоначальное развёртывание с бэкапом. Рабочая домашняя БД и
пользователи не переносятся на VPS автоматически.

PostgreSQL остаётся в контейнере с постоянным томом в 1.0. Нативный PostgreSQL и
готовая система контроля бэкапов/проверки восстановления отложены за 1.0 (#70).

Основания: [Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/),
[Compose в production](https://docs.docker.com/compose/how-tos/production/),
[автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).
