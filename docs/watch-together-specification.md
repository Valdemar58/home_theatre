# Комната, планирование и совместный просмотр

Версия 1.0 · 11 ноября 2026 года. Решения Q1–Q21 и общее понимание подтверждены пользователем.

**Статус:** согласованная базовая спецификация. Grilling завершён: пользователь подтвердил «Да, общее понимание достигнуто». Документ служит основой поэтапной реализации и приёмки. Продуктовый код в рамках подготовки документа не изменялся.

## 1. Цель и границы

Два человека договариваются о просмотре, составляют вечер из нескольких аниме, входят в плеер и смотрят без переходов в загрузки, повторного подтверждения готовности после каждой серии и ручного восстановления после каждого сетевого сбоя.

Целевое развитие: центральный сервер отвечает за пользователей, каталог, планы и координацию; desktop на Windows/Linux получает и подготавливает файлы. Другой участник смотрит через браузер, без установки desktop. Авторизация и членство в комнате обязательны в первой версии. Анонимные ссылки — вне первой версии.

**Порядок внедрения согласован:** сначала комната, редактор и совместный просмотр поверх существующего медиабэкенда; desktop, регистрация устройств, передача видео и автоматическая смена медиахоста — следующие вехи. UI не должен выдавать существующую индивидуальную сессию Jellyfin за полноценный desktop-хостинг.

В одной комнате разрешены несколько будущих сеансов, но только один активный просмотр. План начатого сеанса фиксируется. Обычный редактор не переставляет активные тайтлы/серии; управление перерывом, воспроизведением и автопереходами находится в плеере.

Существующие функции не удаляются. Jellyfin/*arr сохраняются до готовности проверенной альтернативы. Связанные решения по карточке тайтла, франшизе, загрузкам, обсуждениям и ИИ описываются существующими документами; эта спецификация подробно определяет комнату и совместный просмотр, а не заменяет весь продуктовый roadmap.

| Термин | Значение |
|---|---|

| Сеанс | Запланированный вечер: дата, временная зона, упорядоченные тайтлы, выбранные серии и перерывы. |
| Активный просмотр | Исполнение одного зафиксированного плана с общей временной шкалой. Не равен постоянной комнате. |
| Организатор | Владелец комнаты/планирования. Не обязательно хранит медиа. |
| Управляющий | Участник с правом менять воспроизведение, отменять переходы и продолжать без отстающего. |
| Медиахост | Разрешённое владельцем устройство, предоставляющее конкретную версию серии. Не равен организатору. |
| Зритель | Пользователь с подключённым плеером; одно устройство просмотра должно иметь определённую идентичность подключения. |
| Блокирующий зритель | Уже подключившийся к текущему просмотру участник, из-за которого комната может остановиться при потере готовности. |
| Версия | Конкретный источник с совместимой временной шкалой; одинаковое название аниме не доказывает совместимость. |
| Личный прогресс | История конкретного пользователя, его статус просмотра/пересмотра, просмотренные серии и позиции. Не копия прогресса группы. |
| Результат встречи | Фактически достигнутый на этой встрече прогресс группы: тайтлы, серии, позиции и итог. Не утверждение, что каждый участник достиг той же позиции. |
| Просмотр вне приложения | Очная встреча или просмотр через сторонний сервис, для которых организатор вручную фиксирует результат и выбранных участников. Не равен потере сети у desktop. |

## 5. Согласованный интерфейс комнаты

### 5.1. Порядок блоков

1. Название, участники и настройки комнаты.
2. Ближайший запланированный сеанс во всю ширину: стопка обложек, дата/часовой пояс, предполагаемое окончание, вход в совместный плеер. Ниже — последовательность тайтлов с сериями, временем начала/окончания и перерывами.
3. Общий раздел очереди, голосования и списков группы с добавлением из личных списков и поиска.
4. Хосты.
5. История сеансов.

Если будущих встреч несколько, главный блок показывает ближайшую; остальные должны быть доступны отдельным компактным списком. Конкретный дизайн этого списка ещё не показан и не считается визуально принятым. При отсутствии плана — компактное пустое состояние и создание сеанса.

Вне строк хостов участники представлены стопками аватарок. Переполнение — `+N`; раскрытие показывает полный список ников и относящиеся к этому месту статусы. Не использовать персональные имена-заглушки в UI. В строке медиахоста ник виден постоянно; онлайн обозначается зелёной обводкой аватарки, офлайн — отсутствием обводки. Статус доступен также текстовой подсказкой и assistive technology.

### 5.2. Предложения, очередь и голосование

- Добавление из личного списка создаёт **предложение** в комнате; личный статус не меняется.
- Предложение попадает в планы/очередь после победы в голосовании или явного добавления уполномоченным участником.
- Включение в голосование само по себе не переводит в планы.
- Тайтл не дублируется при повторном добавлении.
- Перестановка очереди не переключает текущий тайтл активного просмотра.
- Пустое голосование и ничья не создают произвольного победителя.
- Назначение предложенного тайтла в сеанс означает принятие в планы; право назначения не должно позволять обходить ограничения принятия предложения. Точный набор проверок определяется политикой прав.

**Согласованные права новой комнаты по умолчанию:** все участники предлагают аниме, голосуют, раздают разрешённые собственные файлы и управляют воспроизведением. Организатор добавляет в очередь, меняет её порядок, назначает сеансы и приглашает участников; эти разрешения настраиваются. Создание и завершение голосований — только у организатора.

Разрешение медиахосту выдаётся владельцем устройства для выбранного тайтла и конкретной комнаты и сохраняется между сеансами. Организатор не может принудительно включить раздачу чужих файлов. Наличие этого разрешения не означает, что устройство сейчас онлайн.

### 5.3. Хосты и инспектор серии

- Основная группировка — по пользователям/устройствам, а не по сериям.
- Под каждым хостом тайтлы располагаются **вертикально**. Для ближайшего сеанса показываются именно выбранные серии; дальнейшее раскрытие библиотеки не должно подменять готовность плана.
- Квадратик — серия. Цвет кодирует файл: нет копии / скачивается / подготавливается / готова / возможен стриминг. Номер и подсказка обязательны; цвет не единственный сигнал.
- Просмотр группой обозначается отдельно от готовности файла, например галочкой. Нельзя смешивать эти два измерения в один статус.
- В подсказках/инспекторе — версия, серия, размер, фактический прогресс и доступность устройства. Ширина общей шкалы: 80% скачивание, 20% подготовка; это визуальное распределение, не обещание соотношения времени.
- Без наведения нижний блок показывает общую готовность сеанса. Наведение/фокус временно показывает серию. Клик фиксирует; повторный клик по той же серии снимает фиксацию. Зафиксированную серию другие hover не заменяют.
- Высота инспектора зарезервирована; длинное содержимое не вызывает скачки страницы. На узком экране допускается адаптивная высота/внутренняя прокрутка.
- Офлайн-хост показывает последние известные сведения, но его готовые файлы не считаются сейчас доступным источником.
- Если аниме не выбрано, остаются хосты и доступность; выдуманного прогресса нет.
- Скорости получения и отдачи — разные показатели. Скорость скачивания не доказывает пригодность устройства для раздачи.

### 5.4. История

Карточка встречи содержит дату, тайтлы/обложки, выбранные и фактически просмотренные серии, участников, итог и подробности. Состояния: завершён, прерван, отменён; отдельно требуется определить пропущенный сеанс без старта. Отменённая встреча не меняет прогресс. Прерванная сохраняет позицию; сеанс из двух эпизодов не означает, что целый сезон просмотрен.

В карточке различать результат посиделки и личные результаты участников. Если кто-то отключился раньше, у него остаётся собственная история до момента ухода. Позднейшее окончание встречи не дописывает ему оставшиеся серии.

## 6. Редактор сеанса

- Дата, время и именованная временная зона. Время хранить однозначно; переход летнего/зимнего времени обрабатывать явно, а не скрытым преобразованием браузера.
- Несколько тайтлов, порядок и собственный набор серий каждого.
- При добавлении тайтла по умолчанию выбираются все доступные к дате плана серии. При редактировании существующего плана сохраняется прежний выбор.
- «Выбрать серии» раскрывает сетку; только «Сбросить» и «Отметить все», без ручного ввода диапазона.
- Протягивание мыши выбирает диапазон; начав на выбранной серии, снимает диапазон. Обновление основано на снимке выбора на pointerdown, а не хаотичном переключении каждого пересечения. Pointerup вне сетки завершает операцию. Клавиатура и одиночные нажатия остаются рабочими.
- Просмотренные группой серии серые, но выбираемые; выбранность видна отдельно, например рамкой. Невышедшие/TBA не должны маскироваться под просмотренные.
- Перерыв задаётся после тайтла; последний перерыв не прибавляется к окончанию встречи. Предложение: хранить его вместе с блоком, а при перестановке пояснять новое соседство.
- Изменение серий, порядка, перерывов и времени немедленно пересчитывает расписание, включая переход через полночь.
- Настройка исключения OP/ED изменяет **расчёт расписания**, а не автоматически настройку воспроизведения. Достоверные сегменты предпочтительны; оценочные 1:30 + 1:30 допустимы только с пометкой приблизительности.
- Отмена не меняет сохранённый план. Сохранение согласованно обновляет карточку, порядок, интервалы времени и серии в хостах; не переводит личные списки в «смотрю» до фактического просмотра.
- Пустой список тайтлов, пустые серии, отрицательный перерыв и недоступный диапазон не сохраняются.

**Планирование будущего релиза согласовано:** серия выбирается, если объявленная дата выхода не позже начала сеанса. TBA недоступен для выбора. При переносе релиза план сохраняется с предупреждением; запуск недоступной серии блокируется. Нельзя автоматически удалить её из плана или перескочить на следующую.

## 7. Плеер и исполнение плана

### 7.1. Вход и начало

Кнопка «Смотреть» сразу ведёт в плеер. Выбор источника, получение и подготовка выполняются там. Пользователь не обязан открывать сезон в загрузках и отдельно запускать подготовку серии.

Плеер различает доступность медиахоста, готовность потока, подключение зрителя и готовность зрителя. Приглашённый, который не вошёл, не блокирует старт. Опоздавший подключается к актуальной позиции. Первый старт доступен управляющему после необходимой готовности подключённых зрителей.

Сохранить существующую горизонтальную ленту серий и управление внутри плеера. Невышедшая серия может быть доступна для информации, но не для запуска; показать дату/TBA. Названия, превью и описания соблюдают ранее согласованную политику спойлеров. В общих действиях нельзя путать клик по карточке-превью с авторитетной сменой серии всем участникам.

### 7.2. Конец серии и автопереход

- По завершении серия учитывается у фактических зрителей согласно политике прогресса.
- Следующая серия берётся из **плана**, а не «первого следующего playable» каталога. Неготовую запланированную серию не пропускать молча.
- Поверх плеера — плашка на 10 секунд: следующая серия, «Смотреть сейчас», «Отмена».
- Отсчёт/отмена принадлежат общей комнате. Отмена управляющим отменяет переход для всех; два клиента не выполняют один переход дважды.
- При переходе готовность заново не запрашивается. Если поток уже доступен, просмотр начинается автоматически; если нет — сохраняется намерение продолжить автоматически после реальной готовности.
- Кнопки следующей/предыдущей серии и плашка работают внутри сохраняемой fullscreen-обёртки. Переход не должен принудительно закрывать fullscreen.
- Ручной переход вперёд не доказывает просмотр пропущенной серии.

### 7.3. Между тайтлами

Перерыв начинается автоматически. Сервер задаёт единый срок окончания; клиенты рисуют остаток с учётом смещения часов, а не запускают несвязанные таймеры.

Под таймером управляющий может нажать «Смотреть сейчас» или изменить «Автовоспроизведение после перерыва». При включённом автозапуске срок запускает следующий тайтл без повторного подтверждения готовности. При выключенном показывается «Ожидание организатора»; истечение срока само не включает видео. Включение автозапуска после истечения срока действует как разрешение начать. Восстановление вкладки/соединения использует существующий deadline, а не начинает новый перерыв.

### 7.4. Завершение

После последней запланированной серии показать итог. Завершение создаёт ровно одну запись истории и освобождает активный просмотр. Личные результаты и результат встречи записываются отдельно: групповой результат не вычисляется как минимум, максимум или единогласие личных статусов. Сезон не становится «просмотренным» только потому, что закончился план вечера. По Q16 тайтл завершён группой при покрытии всех его серий результатами групповых встреч. Финальная серия сама по себе не завершает тайтл; личные просмотры вне встреч не меняют групповой результат.

### 7.5. Три независимых уровня прогресса

**Принято в Q6:** при онлайн-просмотре у каждого собственные статус (включая «смотрю» и «пересматриваю»), позиция и история. Группа отдельно фиксирует, до чего дошла выбранная встреча. Формулировка «группа посмотрела» относится к результату посиделки, а не к одинаковому прогрессу всех членов комнаты. Предложение предыдущей версии считать группу по всем участникам отклонено.

Пример: встреча дошла до конца серии 7, участник А ушёл на серии 6. У встречи сохраняется результат до 7, у А — фактически просмотренные интервалы и позиция на 6. Участник Б, пересматривающий тайтл, сохраняет собственный статус пересмотра. Новый участник комнаты не должен задним числом изменять результат прежней встречи.

**Окончательное правило Q7/Q12:** автоматическая отметка требует покрытия **не менее 80% полной длительности серии**. Никакие сегменты из знаменателя не исключаются: ни OP/ED, ни титры, ни анонсы, ни размеченные вставки. Предыдущая трактовка «80% содержательной части» ошибочна и отменена. Кнопка «Просмотрено» доступна для каждой серии.

Формула: `D = полная длительность`, `W = union(observedPlaybackIntervals) ∩ [0, D]`; отметка при `length(W) / D >= 0.80`. Перемотка не создаёт просмотренный интервал, повтор одного участка не увеличивает покрытие. При неизвестной или некорректной длительности автоматическая отметка запрещена, ручная доступна. Разметка сегментов и настройка расчётной длительности сеанса не влияют на этот порог.

Проверка границ на иллюстративных длительностях (не статистика релизов):

| Полная серия | Нужно посмотреть | Допустимо пропустить | Пример пропуска и результат |
|---|---|---|---|
| 24:00 | 19:12 | 4:48 | OP/ED 3:00 + прочее 1:30 → 81,25%, зачёт |
| 23:00 | 18:24 | 4:36 | Всего 5:00 → 78,26%, без автоматического зачёта |
| 12:00 | 9:36 | 2:24 | OP/ED суммарно 3:00 → 75%, без зачёта |
| 5:00 | 4:00 | 1:00 | Всего 1:00 → ровно 80%, зачёт |
| 3:00 | 2:24 | 0:36 | Всего 1:00 → 66,67%, без зачёта |
| 1:00 | 0:48 | 0:12 | Всего 0:15 → 75%, без зачёта |

Вывод: 80% — понятный единый компромисс, независимый от качества разметки, но он не гарантирует зачёт всей сюжетной части коротких выпусков. В таких случаях предусмотрена ручная отметка; адаптивный порог не согласован.

### 7.5.1. Автоматические статусы и пересмотр

Проверено по исходникам `apps/anime-calendar`:

- `src/lib/entry-rules.ts:26–43`: увеличение числа отмеченных серий переводит отсутствующую/запланированную/отложенную/брошенную запись в «Смотрю». Отметка не последней серии завершённого тайтла при известном числе серий переводит в «Пересматриваю»; последняя серия завершённого релиза возвращает «Просмотрено».
- `src/server/player.ts:318–327`: текущий триггер — достижение позиции 85%, а не начало воспроизведения или измеренное покрытие. Его нужно заменить новым учётом.
- В серверных обработчиках и периодических задачах не найдено автоматического «Брошено» по неактивности или возврата неактивного пересмотра в «Просмотрено».
- Текущая запись переиспользует один счётчик серий; отдельного цикла пересмотра нет. `src/server/jellyfin-sync.ts:56–61` пропускает запись `logWatch`/`onProgress` при первом переходе completed → rewatching. `watch_log` хранит агрегированные приращения, а не полную историю конкретных серий каждого цикла.

**Требование Q15:** автоматически начинать «Смотрю»/«Пересматриваю» при фактическом начале просмотра; сохранять ранее завершённый просмотр и отдельный прогресс пересмотра. Долгая неактивность первого просмотра ведёт к «Брошено», пересмотра — обратно к «Просмотрено», сохраняя незавершённый цикл в истории. Правила Q19–Q21:

- «Смотрю»/«Пересматриваю» включается после фактического воспроизведения **10% полной длительности одной серии**. Используются реально просмотренные участки текущего просмотра: перемотка до позиции 10% не считается просмотром; старые интервалы завершённого цикла не запускают новый пересмотр. Ручная отметка серии также запускает соответствующий учёт. Порог смены статуса 10% не заменяет порог зачёта серии 80%.
- В инженерной формализации используется объединение просмотренных интервалов: пауза не сбрасывает накопленное покрытие, повтор того же участка не прибавляет проценты. Это толкование «без перематывания» явно подтверждено пользователем при согласовании версии 1.0.
- По умолчанию срок неактивности — **60 дней**; пользователь может изменить срок или отключить автоматическое правило. Первый незавершённый просмотр переходит в «Брошено», неактивный пересмотр — в «Просмотрено» с сохранением истории цикла и ранее завершённого просмотра.
- Если просмотрены все вышедшие серии и ожидается продолжение, ожидание релиза не считается неактивностью. Отсчёт начинается с выхода следующей непросмотренной серии. Временная недоступность источника сама по себе не останавливает отсчёт.

 Старые данные нельзя выдавать за восстановленную точную историю циклов.

### 7.6. Отметка за участников после очной встречи или стороннего сервиса

Это **обязательный дополнительный сценарий**, а не обходной способ синхронизации онлайн-просмотра:

1. Организатор открывает действие отметки совместного просмотра.
2. Выбирает встречу/результат группы и людей, чьё участие он подтверждает. Простого членства в комнате недостаточно; RSVP не подменяет фактическое присутствие.
3. Может использовать достигнутый группой результат или результат выбранной встречи. По Q14 используются конкретные серии зафиксированного результата, не автоматически все серии 1…N. Для внешнего просмотра можно явно выбрать диапазон или отдельные серии.
4. Для выбранных участников записывается отметка просмотра; остальных действие не затрагивает.
5. Система различает отметку организатором и измеренный онлайн-просмотр. По Q13 перед сохранением показываются участники и изменения для каждого. Отметка — отдельное событие с автором и основанием; более поздний прогресс не откатывается, измеренная история не переписывается. Участник может исправить свою отметку. Правила пересмотра см. 7.5.1.

Принятое требование не даёт права автоматически переписать известный ранний уход зрителя: организатор должен явно выбрать его для ручной отметки и подтвердить, что просмотр действительно состоялся иным способом. Макет этого действия ещё не создан. Существующий `together.ts` — кандидат на переиспользование, но не доказательство, что уже реализованы все перечисленные правила.

### 7.7. Несостоявшаяся встреча и исправление истории

По Q18 назначенный сеанс, который никто не начал, получает «Не состоялся» через **два часа после запланированного начала**. Работающий сеанс это правило не завершает. Такой исход сам по себе не создаёт прогресс.

Организатор может исправить запись истории: указать, что встреча состоялась вне приложения, и выбрать реально просмотренные серии. Сохраняются исходный исход, автор, время и новая редакция результата. Повторное сохранение не создаёт вторую встречу или дублирующие отметки. Пересчитывается групповой результат; личные отметки создаются отдельно для явно выбранных участников с предпросмотром по 7.6.

### 7.8. Уход последнего управляющего

По Q17 исправное воспроизведение и уже разрешённые автопереходы продолжаются. Новые права никому автоматически не выдаются. Если требуется ручное решение, показывается «Ожидание организатора»; заранее уполномоченный участник может принять его.

## 8. Обрыв медиахоста и буфер

### 8.1. Успешное автоматическое переключение

1. Обнаружен обрыв. Небольшая плашка внутри плеера; **не ставить немедленную общую паузу только по факту обрыва**.
2. Зрители продолжают читать локальный буфер. Система автоматически ищет разрешённый онлайн-хост нужной версии/серии.
3. Каждый плеер подключается к новому источнику по актуальной общей временной шкале. Позиция обрыва — checkpoint, а не точка обязательного отката: пока буфер играл, общая позиция продвинулась.
4. Когда все подключения успели до исчерпания буфера, просмотр продолжается без кнопки «Продолжить всем» и без повторной готовности.

«Без паузы» — условный результат успешного handover в пределах буфера, не безусловное обещание для любой сети/браузера.

### 8.2. Отстающий зритель

Если у учитываемого зрителя запас исчерпан раньше восстановления, зафиксировать общую паузу и позицию. Если восстановились все — продолжить автоматически. Управляющий может «Продолжить без отстающего», если у продолжающих есть воспроизводимый поток. Отстающий позже догоняет текущую позицию; пропущенный интервал не считается просмотренным.

Приглашённые, но ещё не вошедшие, не участвуют в таком барьере. Потерю управляющего канала зрителя нельзя полностью отождествлять с потерей источника видео: для недоступного клиента известны только последние данные буфера. Граница доверия к этим данным должна быть описана протоколом.

**Решено в Q8:** после команды продолжить без отстающего он исключается из блокирующих просмотр до фактического возвращения, а не до следующей серии. По возвращении синхронизируется и снова учитывается. Нынешнее автоматическое исключение через 90 секунд в новом режиме убирается; решение продолжить принимает пользователь с правом управления.

### 8.3. Нет замены

Другая версия, другая шкала времени, офлайн-устройство или отсутствие разрешения не подходят для незаметной замены. Смотрим имеющийся буфер, затем ждём пригодный источник. Возврат прежнего хоста возобновляет подключение и синхронизацию. Смена на другую редакцию — отдельный явный сценарий, не часть автоматического failover первой версии.

### 8.4. Потеря центрального сервера

Согласовано: первая версия не поддерживает автономное управление комнатой без сервера. После обнаружения потери координации — управляемая пауза, сохранение последней подтверждённой позиции и восстановление по серверному состоянию. Не создавать несколько независимых «главных» плееров. При возвращении связи устаревшие команды не должны переигрывать свежую позицию.

## 9. Предлагаемая модель и протокол

Это инженерное предложение для реализации, не утверждение о существующих API. Имена таблиц/полей уточняются после проверки миграций.

| Сущность | Обязательные данные |
|---|---|
| Room policy | Членство, capability-настройки, организатор, делегирование, версия политики |
| Session plan | ID, room ID, timezone, start instant, revision, lifecycle, автор |
| Session item | Порядок, canonical title ID, набор эпизодов, перерыв, snapshot оценок длительности |
| Active run | ID плана и snapshot revision, текущий item/episode, playing/paused, anchor position/time, state revision |
| Transition | Уникальный ID, причина, target, deadline, autoplay, cancelled/completed, authority revision |
| Host inventory | User/device, доступность, разрешённая комната/тайтл, episode, source/version identity, readiness, last seen |
| Viewer connection | User/device/connection ID, текущая версия, last heartbeat, buffered ranges, position, playback status, участие в барьере |
| Transfer | Source epoch, старый/новый хост, compatibility proof, route readiness по зрителям, актуальный anchor |
| Personal progress | Статус пользователя, позиции и покрытие серий, источник автоматической/ручной отметки; отделены от группового результата; сохраняется завершённый просмотр и отдельные циклы пересмотра; тайм-аут 60 дней, личная настройка и исключение ожидания релиза по Q20–Q21 |
| Attendance | Наблюдённые подключения/выходы, пропуски и подтверждённое организатором присутствие на просмотре вне приложения; отдельно от RSVP |
| Group result | Snapshot достигнутых серий/позиций конкретной встречи, способ фиксации (онлайн/ручной), связь с сеансом; не минимум личного прогресса |
| History | Snapshot плана, фактический итог, серии/участники, причины остановки, ссылки на события |

Инварианты:

1. Сервер — единственный источник порядка общих команд; у команды есть ID и ожидаемая revision. Дубликаты безопасны.
2. Для комнаты не более одного активного run; защита нужна на уровне данных, не только UI.
3. Переход и его отмена проверяются атомарно. Один deadline не запускается несколькими процессами повторно.
4. Новая эпоха источника делает устаревшие ответы прежнего хоста неактуальными; late arrival не переключает поток назад.
5. Совместимость проверяется по идентичности исходной редакции и временной шкалы. Хэш подготовленного контейнера сам по себе недостаточен: remux может изменить байты, не изменив контент. Предлагается identity исходника + параметры timeline/track mapping.
6. Отчёт о последней позиции и фактически просмотренный интервал — разные события.
7. Быстрый тест HTTP доступности хоста недостаточен: пригодность подтверждается открытием нужного потока и готовностью каждого зрителя.
8. UI-кнопки не являются проверкой полномочий: сервер повторно проверяет членство, capability и доступ к источнику.
9. Любая передача файлов ограничена разрешениями владельца устройства. Ссылка на комнату не открывает всю файловую систему.
10. Нужны различимые события: source disconnected, viewer buffering, coordinator disconnected, incompatible source, transfer complete, viewer excluded/rejoined.

| Q10 | Можно планировать известный релиз до начала сеанса; TBA недоступен; перенос даты показывает ошибку, не удаляет и не пропускает серию. |

## 11. Вехи и атомарные задачи

Ниже — предварительная декомпозиция. Заход объединяет 2–3 проверяемые задачи, а не одну крупную «реализовать комнату». Каждый пункт оставляет старый путь рабочим; неготовая веха не включается всем пользователям. Оценки — человеко-дни опытного разработчика, без ожидания внешних доступов и без обещания календарной даты. Поздние оценки существенно зависят от испытаний медиатракта.

### М1. Комната как единый центр планирования — 4–7 дней

**Результат:** пользователи видят предложения, принимают их в планы и управляют существующими списками без потери данных.

- Заход 1.1: `R01` добавить статус предложения и совместимое чтение старых записей; `R02` реализовать явный переход предложение → очередь без дубликатов.
- Заход 1.2: `R03` добавить capability-проверки рядом с прежними presets; `R04` добавить настройки прав и показать отказ для запрещённого действия.
- Заход 1.3: `R05` подключить добавление из личных списков; `R06` переставить блоки комнаты и аватарки, сохранив прежние действия.

**Приёмка:** предложение не меняет личный список; запрещённый queue-add отклоняется сервером; одна запись после повторного запроса; старые группы читаются. **Откат:** флаг нового UI, новая схема остаётся.

### М2. Полноценный редактор будущих сеансов — 6–10 дней

**Результат:** сохраняемый план из нескольких тайтлов/произвольных серий с корректным расписанием и отображением в комнате.

- Заход 2.1: `R07` добавить упорядоченные session items и revision, адаптер старого single-title формата; `R08` добавить серверную валидацию доступности/длительности/права.
- Заход 2.2: `R09` добавить выбор серий и drag без ручного диапазона; `R10` добавить перестановку и перерывы; `R11` добавить расчёт OP/ED с происхождением оценки.
- Заход 2.3: `R12` подключить сохранение/отмену редактора; `R13` обновлять карточку, будущие встречи и серии хостов одним snapshot; `R14` обработать конфликт параллельного редактирования.

**Приёмка:** отмена не пишет данные; изменения переживают reload; полночь/DST покрыты; конфликт не перетирает чужой план; даты перенесённых релизов не позволяют ложный запуск. **Откат:** старые планы остаются исполнимыми; новые multi-title планы не отправляются в несовместимый legacy executor.

### М3. Сквозной сеанс поверх текущего медиабэкенда — 7–12 дней

**Результат:** реальный совместный вечер с переходами и перерывами, без desktop failover.

- Заход 3.1: `R15` зафиксировать snapshot плана при старте и единственность активного run; `R16` связать его с существующим playback anchor/SSE.
- Заход 3.2: `R17` добавить серверный transition ID/deadline/cancel; `R18` брать следующий эпизод из плана и сохранить fullscreen-обёртку.
- Заход 3.3: `R19` реализовать общий перерыв и autoplay toggle; `R20` сохранить намерение autostart при ожидании потока, не требуя новой ручной готовности.
- Заход 3.4: `R21` восстановление вкладки/подключения по серверному состоянию; `R22` управляемая пауза при потере координатора.

**Приёмка:** два реальных браузера исполняют один переход; отмена одного управляющего видна обоим; ноль автоматических пропусков неподготовленных серий; fullscreen не закрывается; после SSE reconnect не повторяется прошедший переход. **Откат:** выбор legacy/new executor для сеанса до его начала, без переключения работающего run посередине.

### М4. Достоверные прогресс, внешние встречи и история — 7–12 дней

**Результат:** история показывает то, что действительно произошло, без ложных отметок при перемотке/опоздании.

- Заход 4.1: `R23` собирать интервалы/присутствие отдельно от позиции и RSVP; `R24` применить согласованную политику завершения серии.
- Заход 4.2: `R25` сделать повторяемое обновление личного прогресса без двойного учёта existing together/Jellyfin; `R26` хранить и выводить независимый результат встречи/группы, не вычислять его по личному минимуму.
- Заход 4.3: `R27` сохранять итог/прерывание/отмену сеанса; `R28` подключить карточки истории и ручное исправление с происхождением.
- Заход 4.4: `R53` реализовать действие организатора для отметки просмотра вне приложения за выбранных участников с проверкой полномочий и предпросмотром; `R54` связать его с личными статусами/пересмотром по Q13–Q15, сохранив измеренную онлайн-историю, отдельные циклы и прежнее завершение.
- Заход 4.5: `R55` добавить хранение циклов пересмотра и прежнего завершения без выдумывания истории старых записей; `R56` включить автоматические статусы по покрытию 10% текущей серии, сохранив независимый порог зачёта 80%.
- Заход 4.6: `R57` добавить личную настройку и идемпотентное правило 60 дней с исключением ожидания релиза; `R58` добавить исход «Не состоялся» через два часа и исправление результата из истории с пересчётом проекций.

**Приёмка:** 9,99% не запускают статус, 10% запускают; перемотка к 10% не запускает его; тайм-аут учитывает личную настройку и ожидание релиза; 79,99% не засчитываются, 80% засчитываются; метки OP/ED не меняют знаменатель; коррекция несостоявшейся встречи не дублирует историю; неактивный пересмотр сохраняет прежнее завершение; повтор ended не дублирует запись; прыжок к финалу не равен просмотру; исключённому зрителю не засчитывается пропущенное; два эпизода плана не завершают сезон; ручная отметка не теряется из-за позднего heartbeat. **Откат:** журнал сохраняется, старая проекция прогресса читается до включения новой.

### М5. Desktop как разрешённый медиахост — 8–14 дней после проверки платформ

**Результат:** Windows/Linux-приложение публикует собственные разрешённые серии и достоверную готовность; пользователь управляет раздачей.

- Заход 5.1: `R29` регистрация устройства/сессии/heartbeat и отзыв доступа; `R30` локальное подключение файла и устойчивые идентификаторы версии.
- Заход 5.2: `R31` явное разрешение раздачи комнате; `R32` локальная подготовка и наблюдаемый прогресс.
- Заход 5.3: `R33` реальный inventory хостов в комнате; `R34` офлайн/старая телеметрия, вертикальные тайтлы и инспектор с pin/unpin.

**Приёмка:** выключенное приложение становится недоступным; чужие файлы нельзя расшарить удалённо; готовность берётся с устройства, не из анимации; отзыв прекращает новый доступ. **Откат:** устройство отключается, исходные локальные файлы не удаляются.

### М6. Desktop → браузер через разные сети — 10–18 дней, уточнить экспериментом

**Результат:** один авторизованный зритель реально воспроизводит файл desktop-хоста через прямой маршрут или предусмотренный relay.

- Заход 6.1: `R35` измерить варианты передачи, кодеки/seek и relay на целевых сетях; `R36` выбрать транспорт по результатам, зафиксировать ограничения.
- Заход 6.2: `R37` реализовать защищённое открытие источника/сеанса и прямой маршрут; `R38` добавить fallback relay и диагностику причины.
- Заход 6.3: `R39` отдавать buffered ranges/позицию/готовность клиента; `R40` пройти сценарий входа по ссылке, отказа доступа и возобновления.

**Приёмка:** реальные Windows/Linux и два независимых подключения к сети; 1080p SDR baseline измерен; ошибки NAT/кодека различимы; неподдерживаемый браузер получает честное состояние. TV/мобильные браузеры проверяются отдельно, не объявляются поддержанными по макету. **Откат:** выбор старого источника; никаких silent upload библиотек на центральный сервер.

### М7. Автозамена хоста и продолжение через буфер — 10–18 дней после М6

**Результат:** обрыв одного устройства не требует ручного handover при наличии пригодной копии.

- Заход 7.1: `R41` проверка source/timeline identity и разрешений кандидата; `R42` выбор кандидата и новая epoch источника.
- Заход 7.2: `R43` независимо переключать зрителей с сохранением общей шкалы; `R44` маленькая плашка и достоверная диагностика запасов буфера.
- Заход 7.3: `R45` общий barrier при исчерпании буфера; `R46` ручное исключение отстающего и поздняя синхронизация с учётом пропусков.
- Заход 7.4: `R47` возврат прежнего хоста, incompatible version и отсутствие копии; `R48` испытания медленного/полностью отключённого клиента и сетевых гонок.

**Приёмка:** при достаточном измеренном буфере нет дополнительной паузы; при недостаточном есть предсказуемая общая пауза; исключённый возвращается на актуальную позицию, а не на checkpoint обрыва; старый хост не перехватывает управление после восстановления. **Откат:** выключить автоматический handover, оставить диагностику и безопасное ожидание источника.

### М8. Закрепление и поэтапный выпуск — 3–6 дней плюс наблюдение

- Заход 8.1: `R49` прогнать согласованную матрицу ОС/браузеров и accessibility; `R50` проверить обновление/обратную совместимость миграций.
- Заход 8.2: `R51` несколько реальных вечеров А/Б с журналом сбоев; `R52` включать новые пути по флагам только после выполнения критериев.

**Результат:** воспроизводимая установка и проверенный сквозной сценарий; известные ограничения отражены в продукте. Сумма диапазонов М1–М8 — **55–97 человеко-дней**, без резерва и без повторного учёта общей desktop-инфраструктуры старого roadmap. Это предварительная оценка конкретной спецификации, уточнённая после добавления отметок внешних встреч; после М6 диапазон М7 пересчитывается. Нельзя трактовать её как дополнение на 55–97 дней к старому общему плану.

## 12. Проверки, наблюдаемость и критерии выпуска

Обязательные функциональные проверки: оба порядка тайтлов; непоследовательные серии; короткий/нулевой перерыв; отмена на границе deadline; переключение в fullscreen; один ушедший viewer; авторизованный и запрещённый control; потеря SSE; host-down до подготовки и во время видео; запас буфера меньше/больше handover; late-join после продолжения; разные версии файла; дубли и перестановка событий; повторное завершение; смена даты/DST; восстановление процесса.

Инженерные **начальные целевые показатели**, не результаты измерений:

- 100% принятых общих команд в сценарных тестах имеют ID/revision; 0 повторных переходов при повторной доставке.
- 0 незаметных переключений на несовместимую версию; 0 ложных отметок просмотра в тестах перемотки/пропусков.
- На целевой матрице устойчивое расхождение воспроизведения p95 ≤ 500 мс; после управляемого seek/переключения стабилизация ≤ 3 с. Пересмотреть после медиапрототипа, если цель конфликтует с возможностями транспорта.
- Handover оценивается относительно **фактически доступного буфера**, а не обещанием фиксированных двух секунд: время восстановления, остаток буфера, длительность stall и причина по каждому зрителю.
- Отдельно измерять задержку обнаружения обрыва, доставки общей паузы, процент relay, расход relay-трафика, длительность подготовки, восстановление после coordinator reconnect.
- UI: без скачков инспектора; критические действия доступны без hover; клавиатура и reduced motion; никакого скрытого выхода из fullscreen при смене серии.

На каждую завершённую задачу: изменённый контракт, позитивный сценарий, один релевантный отказ, границы регрессии и способ отключения. Тесты чистой перестановки кнопок не должны зеркалить JSX; нужны визуальная проверка и проход сценария. Миграции расширяющие, backfill повторяемый, отключение флага не удаляет пользовательские данные.

## 13. Риски и решения, которые нельзя скрыть макетом

| Риск | Последствие | Ограничение / проверка |
|---|---|---|
| Байты той же серии не имеют той же временной шкалы | Скачок сюжета/несинхронная озвучка | Compatibility identity, не только title/episode ID |
| Отчёт буфера устарел | Комната узнаёт о stall поздно | Heartbeat age, timestamped ranges, сценарий полного обрыва управляющей связи |
| Relay фактически становится основным маршрутом | Стоимость и chokepoint | Измерять долю/битрейт, задавать лимиты; не обещать почти бесплатный P2P |
| Локальные таймеры/процессы состязаются | Двойной переход | Авторитетная revision, дедупликация, восстановимый deadline |
| Старое правило 85% пересекается с новым учётом | Ложные отметки и двойная история | Единственный writer/проекция, отдельный rollout политики |
| Desktop закрыт, но UI хранит «готово» | Невозможность запуска | Разделить наличие файла и текущую доступность |
| Расписание OP/ED принято за точную длительность | Неверные ожидания | Источник длительности/погрешность; оценка не участвует в засчитывании просмотра |
| Отзыв прав после выдачи media URL | Просмотр продолжается без полномочий | Короткоживущие разрешения и ревокация на медиатракте |
| Активный план изменён из другого клиента | Зрители переходят в разные серии | Неизменяемый snapshot run и optimistic concurrency будущего плана |
| Макет принят за готовую функцию | Ложное ощущение завершённости | Вехи принимаются по реальным двум клиентам, не по симулятору |
