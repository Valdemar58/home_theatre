# R2 — независимые аккаунты и доступ

Реализованы R2.1–R2.3; результат передаётся владельцу на приёмку. Это не выпуск
1.0. Рабочая база на 5056 не заменяется тестовой, пароль владельца выбирается
им самим в форме настройки. R1 принят 19 ноября 2026.

## Поведение

- Один логин/пароль для веба и desktop; ник задаётся отдельно. Вход не вызывает
  Jellyfin или Authentik. Их медиафункции сохраняются.
- Для серверного PlaybackInfo технический пользователь выбирается в самом
  Jellyfin (действующий администратор или `JELLYFIN_PLAYBACK_USER_ID`). Роли
  home_theater его не определяют. Сохраняется прежняя связь с Jellyfin у старых
  аккаунтов; новые локальные аккаунты не получают общий личный прогресс Jellyfin.
- Саморегистрация открывает только экран «Ожидает одобрения». Защищённые API
  и страницы до одобрения недоступны. Администратор одобряет или отклоняет заявку
  в «Аккаунты и доступ»; уже открытый экран ожидания сам проверяет решение.
- Одноразовое приглашение с TTL сразу даёт обычный доступ после регистрации.
  Администратор может отозвать ссылку. По умолчанию срок — 7 дней; API допускает
  1–720 часов. Приглашение в комнату отдельно требует принятия членства.
- Администратор блокирует/возвращает доступ, меняет роль, завершает все входы,
  выдаёт одноразовую ссылку восстановления. Блокировка не удаляет историю.
  Нельзя заблокировать себя или лишить систему последнего администратора.
- Восстановление пароля завершает прежние браузерные сессии, включая открытые
  потоки событий. Постоянная привязка desktop сохраняется. Пока доступ заблокирован,
  токен устройства не разрешает работу от имени пользователя.

## Переход существующего admin

Перед обновлением необходима резервная копия PostgreSQL и сохранённая конфигурация.
Команды выполняются владельцем на сервере, ссылка не публикуется в Issues/логах CI.

1. В согласованное окно установить сервер с R2. Миграция добавляет таблицы,
   не пересоздаёт пользователей, историю, списки или устройства.
2. Выпустить ссылку для **существующего** пользователя, а не регистрировать нового:

   ```sh
   docker compose exec anime-calendar node database/account-admin.mjs claim-admin --user-id 1 --base-url https://YOUR_SERVER
   ```

   Если ID отличается, подставить фактический. Без `--user-id` команда допускает
   ровно одного действующего администратора. Ссылка действует один час.
3. Открыть ссылку, выбрать собственные логин, ник и пароль. ID пользователя,
   его роль администратора, статусы просмотра, история и привязки сохраняются.
   Внешний пароль не переносится. После настройки войти этим же аккаунтом в desktop.
4. Проверить свои списки, комнаты и список устройств. Повторно привязывать уже
   привязанный desktop не требуется. Старая браузерная сессия потребует нового входа.

Старый способ входа выключен по умолчанию. `LEGACY_AUTH_ENABLED=1` допускает
переходное использование внешнего входа только до появления первого одобренного
локального аккаунта. После этого он больше не может изменить локальные роли.
Старое поле `jellyfin_id` остаётся для совместимости данных, а не проверки пароля.

На чистой установке после запуска миграций вместо `claim-admin` используется
`create-owner`: новый владелец создаётся только если нет администратора или
одобренного аккаунта. Публичная регистрация сама по себе администратором не делает.

## Восстановление доступа без почты

```sh
docker compose exec anime-calendar node database/account-admin.mjs reset --user-id 1 --base-url https://YOUR_SERVER
```

Либо другой администратор выдаёт ссылку через интерфейс. Новая ссылка отменяет
предыдущую неиспользованную. Внешние ссылки требуют HTTPS; локальная проверка
допускается через `http://127.0.0.1:5057`. Для SQLite команда принимает `--sqlite FILE`.

## Защита

Пароли: scrypt с индивидуальной случайной солью. В базе находятся только хеши
паролей и одноразовых токенов. Использование токена транзакционное; повтор,
истечение срока и отзыв запрещены. Секретная часть ссылки передаётся во фрагменте
URL, удаляется из адресной строки формой и отправляется POST-запросом.
Ссылка показывается при создании; из сохранённого хеша восстановить её нельзя.

Проверяются Origin, размер тела, формат логина и пароля; ограничения попыток
сохраняются в БД. Прокси должен сохранять Host и выставлять корректный протокол.
HTTPS-сессия получает Secure/HttpOnly/SameSite=Lax cookie. `SESSION_SECRET` должен
оставаться постоянным и секретным. Изменения доступа записываются в account_audit.

## Доказательства и границы

- Изолированная копия рабочей PostgreSQL: после миграции и настройки admin
  сохранён ID 1; сравнение 103 прежних таблиц не выявило изменений данных,
  кроме намеренной смены ника. Файлы копии и одноразовые ссылки не включены в Git.
- Проверены: одинаковая идентичность и токен устройства после миграции, регистрация
  с/без приглашения, одобрение/отказ, TTL/отзыв/повтор ссылки, смена пароля, отзыв
  сессий, блокировка устройства, защита последнего администратора, восстановление CLI.
- В Electron и Chromium на отдельной синтетической установке проверены настройка
  владельца, привязка desktop, экран ожидания, одобрение, регистрация по приглашению.
  Формы и админка проверены на ширине 390 px без горизонтального переполнения.
- Тесты PostgreSQL и SQLite не заменяют принятие владельцем своего интерфейса.
  Arch остаётся preview; реальная проверка GUI на Arch ещё не проведена.
- Это веха аккаунтов. Автоматизированный установщик и обновления продукта остаются
  последующими вехами. Пересмотр архитектуры модулей и аккаунтов standalone не включён.

Финальный прогон: 589 тестов PostgreSQL, 741 статический SQL-запрос; 588 тестов
SQLite (один предназначен только для PostgreSQL); 16 native-тестов
desktop. [CI R2](https://github.com/Valdemar58/home_theatre/actions/runs/44620227727)
проверяет сервер и desktop на Windows/Linux, сборку Next и историю на секреты.
После последующих изменений обязательным остаётся последний CI конкретного коммита.

main `bb8ffb82adb4cbebfa99cf2bd1cd3820e58fd190`. Проверка GitHub Dependabot
после слияния: **0 открытых предупреждений**. Задачи R2 переданы на проверку,
их пользовательская приёмка ещё не выполнена. Рабочая установка 5056 не обновлена.

## Приёмка владельцем

После согласованного обновления рабочего сервера: настроить существующий admin,
проверить собственные списки и устройства; войти из desktop; создать тестовую заявку,
одобрить её; создать приглашение и убедиться, что второй раз оно не работает;
проверить отзыв доступа. Написать «R2 принято» или перечислить замечания.
Агент затем синхронизирует чек-листы, доску и Issues #8, #9, #10.
